# 问题、经验与工程实践

## 关键问题

现有方法设计可以提炼出以下工程问题。它们是健康检查体系的通用经验，不代表生产集群已经发生或完成闭环。

| 问题 | 直接影响 | 技术原则 | 仍需生产验证 |
| --- | --- | --- | --- |
| 大规模静态检查产生大量小对象 | 共享存储元数据压力、聚合慢 | 本地暂存原始明细，共享层保存聚合与异常证据 | 千节点并发时控制面和共享存储负载 |
| 结果截断或不完整 | 可能把缺失结果误判为通过 | 校验来源、长度和完整性摘要；缺失与测试失败分开记录 | 平台传输限制和恢复耗时 |
| 单次带宽低谷误伤健康节点 | 误隔离、降低资源利用率 | 同类群体比较、冻结用例、相邻消息规模和多批次复测 | 不同拓扑与负载下的阈值和误报率 |
| 多节点故障只表现为“某组失败” | 根因节点不明确 | 成对换伙伴、物理链路控制组和确定性随机种子 | 大规模定位时间与控制面压力 |
| 把两节点矩阵直接放大到千卡 | 产生训练中不存在的全局 All-to-All 和连接资源压力 | 按实际 Megatron 并行关系形成真实训练通信组 | 通信组定义与训练版本的一致性 |
| 大候选池无法直接组成目标拓扑 | 随意缩容或选卡会改变结论 | 多阶段覆盖后精确划分入选、备用和排除集合 | 风险排序与业务策略复核 |
| 长控制连接不稳定 | 控制连接抖动可能误判任务失败 | 将准备、统一激活和结果回收解耦，并设置阶段检查点 | 千节点控制面与恢复时长 |

## 有效实践

- **先预演再执行**：先核对计算实例、节点、rank、运行环境和实验条件，适合发现编排错误；预演本身不验证设备或通信健康。
- **正确性与性能分轨**：NaN/Inf、checksum、建联、进程、超时和传输失败是硬失败；相对低带宽先作为候选复测，减少把瞬态拥塞当坏卡的风险。
- **同批横向比较优先**：在硬件、规模和软件版本未完成绝对标定时，以同 case cohort 建立基线；前提是多数样本健康，系统性事件需另行识别。
- **首轮与复测数据分离**：复测计划一次性冻结，复测不覆盖首轮，避免观察结果后不断改变检验条件。
- **训练拓扑复验兜底**：成对测试通过只用于硬件与链路准入；最终按真实 TP/DP/EP/PP 子组完成训练拓扑检查，再进入短程训练。
- **配置成为证据**：策略集中到经过严格校验的结构化配置，并保存最终生效版本；未知字段和已废弃参数显式失败，减少静默漂移。
- **完整数据与准入 gate 分离**：失败后可以继续采集不受影响的 group，但 `BLOCKED/FAIL/SUSPECT` 不因后续有数据而自动恢复。
- **保留失败，压缩成功**：共享存储保留聚合结果与失败证据，详细原始数据在计算实例释放前按策略回收；同时保留足够的成功样本用于审计。
- **把关联成本移到查询侧**：采集器在 rank 本地独立写入，只共享 step、rank、并行角色和时间坐标；避免为了观测引入新的全局同步点。
- **常驻观测与深度采集分层**：持续路径先定位异常 step/rank/module，原始 kernel、stack 和通信 task 只在窄窗口下钻；观测预算随问题范围而不是集群卡数增长。
- **确定性跨 rank 采样**：用 step 和 layer 的稳定键决定命中，使各 rank 选择相同 step，保留可比较的层关系和异常覆盖。
- **结果与质量收据同行**：任何跨 rank 汇总同时返回期望/实际成员、失败分区、丢弃事件和 partial 状态；部分数据可用于定位，但不能静默进入正式 gate。
- **原生适配器留在边缘**：公共训练语义依赖 Torch 和稳定表契约，HCCL/NCCL 等 ABI 变化限制在独立插件，避免厂商版本差异扩散到分析层。

## 未奏效的尝试

- 把其他硬件或节点规模的固定 BusBW 门限直接用于 C550/MCCL，会把正常基线判为失败。绝对门限必须按硬件、拓扑、通信库和消息语义重新标定。
- 用一次最低带宽作为 gate 对瞬态抖动过于敏感。All-Reduce absolute gate 使用次低值与平均值；跨组性能筛查则采用多 batch 的 `avg_busbw` 复测。
- 用小消息 latency 偏离自动阻断准入容易受到启动、同步和 host 抖动影响。默认仅记录小于 1 GiB 的性能，正确性仍照常阻断。
- 仅凭 debug 日志中出现某个 HCA/rail，不能证明各 rail 实际流量或均衡性；需要 counter 和交换机遥测补证。
- 只保留最终 PASS/FAIL 会丢失诊断路径。首轮候选、复测、瞬态恢复、复测新增观察和系统性事件需要分别保留。
- 把 Ascend 主机侧 RoCE 接口差异直接作为训练网卡硬失败会误伤包含存储/业务接口的节点；主机 sysfs 只作诊断，NPU 训练网卡使用专用工具验证。
- 在所有 rank 上持续开启完整 op/kernel/stack 采集，会让写入、网络和分析成本随原始事件数增长；应先用低密度事实缩小 rank 与时间窗。
- 把多个 rank 的原始表直接拼接后执行全局 JOIN 或窗口函数，容易得到语义错误且不可控的结果；应先在数据所在 rank 完成可验证的局部关联，再归并有界状态。
- 直接累加重叠的 module、kernel 或 collective duration 会得到超过 step wall time 的占用；时间占用必须先做区间并集。
- 只报告查询成功而不报告缺失节点和丢弃事件，会系统性低估尾部问题；partial 结果必须附质量收据。

## 组织与流程经验

资产/调度团队提供不可变的 pod-to-node 与故障域快照；平台团队维护执行、结果传输和超时；硬件/网络团队解释 ECC/RAS、HCA 与交换机证据；训练团队负责 Megatron 复现、数值一致性和端到端影响；报告数据评审者核对从 run 到结论的链路。

门限、消息矩阵、分组算法、状态语义、ECC 策略、训练拓扑或节点选择规则的变化都属于结果口径变更，应同时更新方法版本、最终配置、实验记录和报告修订历史。故障注入应作为检测体系发布前回归，至少覆盖 NaN、数值损坏、超时、backend 初始化、rank 退出、通信环境错误和结果传输异常。

## 可复用清单

### 部署与变更后

- [ ] 对账资产、节点、设备、故障域和 pod 映射。
- [ ] 冻结驱动、通信库、框架、运行环境和测量方法版本。
- [ ] 完成执行前预演，人工检查 rank、运行环境和实验条件。
- [ ] 验证结果完整性、缺失证据恢复和失败日志保留策略。

### 扩容与训练前

- [ ] 完成静态检查与单节点动态检查。
- [ ] 按固定随机种子运行多节点分组，保留冻结复测计划。
- [ ] 处理硬失败和持续性能候选；补充宿主机与交换机证据。
- [ ] 完成精确节点准入和真实训练拓扑检查，再执行 Megatron 短程训练和检查点恢复。

### 训练中与训练后

- [ ] 用 run/job/node/rank/device 主键关联训练、健康检查、告警和工单。
- [ ] 保留端到端时间分解，不只看稳态 step 吞吐。
- [ ] 记录观测模式、采样率、rank/step 覆盖、丢弃事件和端到端开销。
- [ ] 先从作业概览定位异常集合，再对少量 rank 和窄时间窗获取深度事件。
- [ ] 故障后先保存现场与拓扑，再清理、隔离和复现。
- [ ] 维修或配置修正后从静态检查重新准入。
- [ ] 将已评审聚合导入[结果章节](08-results-and-analysis.md)，保留原始证据位置与哈希。
