# EXP-007：A3 前向进展 Stall 定位与缓解

## 目的

将 A3 单卡零通信长循环、训练影响、节点热点剔除、ftrace 根因和临时优化材料合并为一条证据链，区分“停顿发生”“根因已定位”“缓解有效”和“硬件应被排除”四种不同结论。

## 最小探针与事件率

探针在每张卡上独立循环执行 `512 x 512` FP16 矩阵乘并调用设备同步；相邻两次同步返回的墙钟 gap 大于等于 200 ms 记为一次 Stall。正常单次约 0.087 ms。该口径测量 CPU、运行时、驱动、设备执行、完成通知与同步返回的整条前向进展链，不是纯 GEMM kernel 时间。

| 规模 | 观察时长 | 事件数 | 事件率 |
| ---: | ---: | ---: | ---: |
| 1,024 卡 | 19 min | 7,658 | 0.393 次/卡/min |
| 512 卡 | 30 min | 6,972 | 0.454 次/卡/min |

事件宽度的 min/P50/P90/max 为 200/504/697/822 ms，主要形成约 500 ms 与 640--690 ms 两簇。把矩阵工作量扩大 512 倍后，异常宽度仍约 605--691 ms，说明尾部不随 GEMM 计算量同比增长。

空间分布高度不均匀：1,024 卡轮次中 76.1% 的卡没有事件，单卡最多 421 次；512 卡轮次中最热 10% 的卡贡献 88.9% 的 Stall 总时间，约一半卡没有事件。这支持按节点和 CPU/IRQ 绑定检查空间聚集；永久硬件隔离由跨轮次、跨负载和厂商诊断共同决定。

## ftrace 根因链

根因报告把异常闭环到 Linux IPVS 的 `estimation_timer`：在 256 核主机上，该回调约占用 871--875 ms 的 `TIMER_SOFTIRQ`；同 CPU 上 NPU CQ 中断到达后虽已调度 tasklet，但 tasklet 需等待 timer 返回。一个代表窗口中：

1. `estimation_timer` 于 `17369167.895814` 进入；
2. NPU CQ IRQ 于 `17369167.895909` 到达；
3. timer 于 `17369168.771255` 返回；
4. `ksoftirqd` 约 8 us 后被唤醒，CQ tasklet 延迟 875.392 ms 后执行，约 988 us 完成；
5. 用户态同步在约 2 ms 内恢复。

报告分析了 5 次 Stall，其中 3 次具有直接 timer/CQ 配对，2 次因 trace buffer 溢出丢失 timer 记录，按约 2.94 s 的复发周期推断。完整 trace 摘要报告 timer 95/95、tasklet 65,800/65,800、softirq 66,037/66,037 成对。该链路解释了“设备计算未变、主机同步长等”和“只影响 CQ IRQ 与 timer 落在同一 CPU 的设备”。在这些样本内，根因收敛到主机软中断与 NPU CQ tasklet 竞争路径。

## 缓解与消融

系统级处置优先级如下：

- 将 NPU CQ IRQ 移离命中 IPVS timer 的 CPU，可使被测设备的 Stall 立即消失；这是降低碰撞概率的缓解，不是消除 IPVS 回调。
- 来源建议把 kube-proxy 从 IPVS 切换到 iptables，或在支持的内核中关闭/隔离 IPVS estimation；这些方案需要按服务规模、内核和 Kubernetes 版本另行验证。
- 训练侧 `TASK_QUEUE_ENABLE=2` 和 jemalloc 可以降低同步暴露与主机分配开销，但不修复内核 timer 根因。

固定热点节点、统计 step 3--500 的文档级消融如下：

| 配置 | 重复 | 平均窗口耗时（ms） | 相对基线 |
| --- | ---: | ---: | ---: |
| baseline | 2 | 234,447.8 | 100.00% |
| TaskQueue level 2 | 3 | 188,643.4 | 80.46% |
| jemalloc | 3 | 207,358.9 | 88.45% |
| TaskQueue level 2 + jemalloc | 3 | 172,215.2 | 73.46% |

组合相对基线缩短 26.54%。这些是整段窗口总耗时，不是单 step latency；baseline 仅两次，运行顺序和原始逐步数据按来源材料管理，因此本记录报告观察性改善，不报告置信区间。来源对 THP 的讨论属于机制假设，后续以同口径结果表登记。

## 节点热点剔除是否可迁移

同一批 512 卡按探针 Stall 热度排序，剔除 4 个节点后用 448 卡训练。完整 512 卡组与 448 卡组 world size/GBS 不同，只作为背景；热点剔除、冷点剔除和三个随机剔除组之间才是主要比较。

| 工作负载 | 热点剔除中位 step（ms） | 三个随机组（ms） | 冷点剔除（ms） | 解释 |
| --- | ---: | --- | ---: | --- |
| 125M 纯 DP | 372 | 361 / 519 / 646 | 829 | 随机方差很大，热点组不是最佳 |
| 8B Dense TP4/PP4 | 4,828 | 5,126 / 5,155 / 5,364 | 5,559 | 热点组比随机组快约 5.8%--10.0% |
| MoE EP32 | 30,996 | 26,615 / 29,882 / 30,660 | 33,502 | 热点组不优于随机组 |

8B Dense 与 MoE 各组约在 step 26 出现 NaN，表中只统计 step 5--25；随机组只有 3 次。结论是探针热度与部分 Dense 训练尾部相关，但不是跨模型通用的节点质量分数。根因落在主机软中断和 IRQ 共核后，调度与 IRQ 隔离比永久拉黑热点节点更符合证据。

## 适用范围

- A3 在给定软件栈和同步探针下存在高频 200 ms 以上前向进展 Stall；该事实描述同步返回链路，不等同于设备 kernel 计算变慢。
- IPVS timer 与 NPU CQ tasklet 的因果链在来源报告中闭环，原始 ftrace 作为受控证据包复核。
- profiler/插桩会显著改变事件率，深度采集配套无插桩控制组；同步间隔本身也会改变尾部。
- 热点节点剔除在 8B Dense 中显示稳定方向；MoE、其他负载和永久硬件隔离策略使用独立复核。
- 训练吞吐降至约 8.1% 是特定 1,024 卡 GPT2-124M 场景的有效吞吐估计，与 Qwen3-200B 主结果分开登记。
