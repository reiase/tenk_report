# EXP-011：大规模健康检查耗时与运行时优化

## 目的

把千卡健康检查的总墙钟拆解为 Pairwise 执行波次、共享存储竞争、round barrier、超时清理、复测、单组固定成本和结果回收，并记录 64 节点同拓扑优化前后的完整流水线对比。

## 正常 Pairwise 成本

128 节点专项实验把 64 个 Pairwise group 拆成控制面与真实 collective：

- 并发 32 时，64 个 no-op group 约 4 秒完成，单次控制连接 p50 约 0.6--0.9 秒、p95 约 1.2--2.0 秒；没有证据支持“单次建连本身需要数分钟”。
- 并发 32 的真实两节点通信在小消息矩阵和 1 KiB--2 GiB、22 档消息矩阵下分别约 74.58 秒和 75.71 秒；扩展 payload 只增加约 1.1 秒。
- 单组生命周期中位数为 34.65 秒，其中 Pod 内动态测试 19.68 秒，占 56.60%；外层 driver、连接、进程与结果回收 15.04 秒，占 43.40%。
- Pod 内 19.68 秒进一步分为 process-group 初始化 6.02 秒、工作负载 11.83 秒和销毁 1.83 秒。

因此，千卡总耗时主要由 group 数量、执行波次与尾部同步放大，不是稳态 collective payload 简单乘卡数。

## 主要放大器

1. **共享 AFS 热写**：历史任务在启动 group 前向共享 AFS 上的 SQLite 写 `group_start`，锁等待进入记录耗时，但 collective 超时计时在进程启动后才开始。因此约 2,593--2,616 秒的记录混合了数据库等待、启动、真实执行和清理，不能解释为 collective 运行了 40 多分钟。
2. **Pairwise 执行波次**：稳定并发 32、每波约 35 秒时，128/256/292 节点分别需要约 2/4/5 波；2,048 节点的单轮 1,024 个 pair 理论约 32 波、19 分钟。后者是模型估算，不是实测 SLA。
3. **round barrier**：每轮必须等待最慢 future 才能进入下一轮或下一 phase，少量 TIMEOUT 形成 head-of-line blocking。
4. **超时与复测**：300/420 秒硬超时、进程清理、换伙伴、拆分定位、3-batch 性能复测和拓扑定向复测会二次放大墙钟。
5. **结果传输**：compact frame 截断可触发重跑，但第二轮 A3 4,096 卡约 130 分钟流程中，相关复测约 170 秒、占 2.2%，不是首要瓶颈。

两个 A3 4,096 卡 Job 的多节点阶段分别约 139 分钟和 7,799 秒，Pairwise 各有 23 和 22 个 TIMEOUT；C550 292 节点的 Pairwise 最终有效轮约 257.9 秒，而 256 节点拓扑阶段约 3,203.9 秒，主要被 Scale8 的 6 个 TIMEOUT 拉长。不同 Job 的主瓶颈不能用一个平均值覆盖。

## 64 节点完整流水线对比

两轮都使用 64 节点、1,024 ranks 和 TP4/EP64/ETP1/PP4/CP1，并执行 Pairwise、EP8、Scale16、Scale32 和 Final64：

| 版本 | Pairwise 基础组 | 多节点墙钟 | Final64 | 结果 |
| --- | ---: | ---: | --- | --- |
| 旧版历史基线 | 41 | 1,706 秒 | 首轮 903.844 秒后 TIMEOUT；独立复测 73.699 秒通过 | 流水线含一次真实长尾成本 |
| main 优化版 | 40 | 1,056 秒 | PASS | 全部计划阶段完成 |
| 差值 | -1 | -650 秒（-38.1%） | 未再次命中固定硬超时 | 观察到的完整流水线改善 |

38.1% 不能全部解释为软件优化的纯收益：两轮使用不同 Job 和物理节点，物理超节点与 Pairwise 计划不同，控制面/HCCL/后台负载不同，基础组数也相差 1；最重要的是旧版 Final64 的约 900 秒长尾没有在优化轮复现。该数字只报告为**受混杂影响的一次端到端墙钟对比**。

## 保留在 main 的机制

- Pod 内任务先后台启动，收到 launch acknowledgement 后断开短连接；collective 不再依赖长时间 stdout 连接。
- SQLite、高频状态、group 输出和结果分块写开发机本地 `/tmp`，每阶段只向共享存储写少量压缩检查点，结束后一次性发布最终报告树。
- 状态机区分 `PREPARED`、`ACTIVATING`、`RUNNING`、`RESULT_READY` 和 `COLLECTED`；只有 `RUNNING` 时间进入 collective 长尾判定。
- 同类 cohort 完成比例达到 70% 且至少有两个成功样本后，以成功任务平均运行时间的 3 倍、最低 60 秒识别长尾，并保留固定硬超时作为绝对上限。
- 结果按 32 KiB 分块读取，校验分块、完整 frame 和解压 payload 的长度与 SHA256；缺块只重取对应结果，不重跑 collective。

## 结论边界

- 健康检查运行时 SLA 与设备健康状态分开：超出目标可记 `WARN`，不能自动把节点判为硬件失败。
- 1,706→1,056 秒是不同 Job 间的完整流水线观察，不是随机化同节点 A/B，也不报告置信区间。
- 本地热数据和分块回收降低控制/存储放大，但不会修复真实 HCCL/MCCL、RDMA、correctness 或设备故障。
- 生产发布前仍需在同一节点集合上交错旧/新实现，固定 Pairwise 计划与后台负载，并分别报告 P50/P95/Max 和失败率。
